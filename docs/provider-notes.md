# Provider implementation and acceptance notes

The backend is implemented locally. Fixture tests exercise real REST envelopes and field names, durable state, explicit demo actions, and OIDC protocol flows. No authentic Proxmox, OPNsense, SSH, or OIDC-provider runtime acceptance has been performed. No infrastructure changes, commits, pushes, PRs or deployments were made by this implementation task. UI, design approval, embedded assets and integration remain parent-owned.

The frontend contract is [backend-api.md](backend-api.md). Backend source is portable and lives in `go.mod`, `go.sum`, `cmd/dashboard/main.go`, `cmd/dashboard/main_test.go`, and `internal/dashboard/`.

## Exact adapter shapes

Proxmox uses `Authorization: PVEAPIToken=<tokenId>=<secret>` and `/api2/json` response envelopes with a required non-null `data`. Reads are `/access/permissions?path=/`, `/nodes`, `/cluster/status`, `/cluster/resources?type=vm`, `/nodes/{node}/lxc/{vmid}/config`, and, for running guests, `/nodes/{node}/lxc/{vmid}/interfaces`. Cluster-wide propagated `VM.Audit` at `/` is required before any completeness/free-slot claim. The node must exist and be online; non-quorate cluster state is refused. Operators must grant unfiltered cluster-wide audit access and avoid overriding denies that make inventory permission-filtered. The dashboard cannot detect an appliance that silently returns false or omitted authoritative data.

The host owns the inclusive allocation interval and network/MAC prefix. Allocation counts all returned cluster LXC and QEMU, across nodes and statuses, including templates. It does not call Proxmox `nextid`. No slot is returned on failed/incomplete reads. Managed inventory lists each configured node's containers, including stopped containers and templates. Configure each node to cover the intended cluster; migration outside a configured node still blocks cleanup via cluster occupancy. MAC/IP reconciliation uses net0; multi-NIC selection is not implemented.

OPNsense uses HTTP Basic authentication with API key/secret over verified HTTPS. Searches use GET `?current=1&rowCount=-1`, require exact `total == len(rows)`, and re-read each row through the getter. Option/relation dictionaries are normalized to selected keys, so translated labels are never mistaken for UUIDs. Full resource fields are fingerprinted, including nested reservation options. Only the global Caddy ACL/enabled references are retained from general settings; general credentials are never returned or persisted in snapshots.

| Resource | Controller | add/get/set/del suffix | JSON body wrapper | Written model fields |
| --- | --- | --- | --- | --- |
| Reservation | `kea/dhcpv4` | `reservation` | `reservation` | `subnet`, `hw_address`, `ip_address`, `hostname`, `description` |
| ACL | `caddy/reverse_proxy` | `access_list` | `accesslist` | `accesslistName`, `clientIps`, `accesslistInvert`, `RequestMatcher`, `HttpResponseCode`, `description` |
| Domain | `caddy/reverse_proxy` | `reverse_proxy` | `reverse` | `enabled`, `FromDomain`, `DisableTls`, `CustomCertificate`, `accesslist`, `description` |
| Handler | `caddy/reverse_proxy` | `handle` | `handle` | `enabled`, `reverse`, `HandleType`, `HandleDirective`, `ToDomain`, `ToPort`, `HttpTls`, `HttpTlsInsecureSkipVerify`, `description` |

For example, adding a reservation sends `{ "reservation": { "subnet": "<UUID>", "hw_address": "d0:cc:37:00:06:12", "ip_address": "192.168.6.12", "hostname": "jellyfin" } }` to `/api/kea/dhcpv4/add_reservation`. Creates require `result:saved` and a UUID; deletes require `result:deleted`. Service application uses only `/api/{kea|caddy}/service/reconfigure` and requires `status:ok`. The upstream KEA reconfigure implementation may stop/start the service internally; Caddy supports reload. No explicit start, stop, restart, plugin installation or global firewall/DNS/TLS mutation is issued. Both services must already be enabled and running during route planning/recovery. Read-only ACL/subnet discovery is independent of daemon status. Operators should account for upstream KEA application interruption before applying changes.

`subdomain` resources are read for dependency protection and never created or deleted by the dashboard. Unrelated domain/subdomain/handler/global ACL references block cleanup. Resource UUID and the last verified complete fingerprint establish ownership. A matching name, comment, IP, hostname or MAC alone never establishes ownership.

## Creation identity, stale plans, and recovery

On current LXC versions without a trustworthy creation field, set a unique `container-dashboard-generation=<UUID>` marker in the Proxmox description before requesting mutations. This is an explicit operator prerequisite, not an automated Proxmox write. Use a new UUID after recreation; never copy it into another generation or cloned container. Duplicate observed markers on one node are rejected. An actually supplied valid `meta.ctime` is also understood, but is not assumed to exist. Inventory remains useful without either source; ensure/update actions are refused. Identity additionally binds configured host, node, VMID, stable root-volume identifier and MAC. Resizing retains identity while the changed configuration digest invalidates stale actions. A node/root-volume change requires inspection and deliberate reenrollment rather than automatic migration or adoption. Cross-node cloned-marker policing and a guided enrollment/migration UI remain integration work.

Per-container desired route scheme, port and public state are persisted with ownership and exposed in inventory/reconciliation. Ensure accepts optional scheme/port overrides; omitted values retain the recorded per-container target or initialize explicit HTTP/80 values. Existing owned domains/handlers retain their UUIDs during reviewed port/scheme/public/private changes. Unowned matches stay conflicts. Plans include concrete resource effects, before/after field changes, resource UUIDs, new dependency markers and service-application notes. An entirely matching plan performs no provider write/reconfigure; changed plans describe temporary domain staging before final enablement.

Plans pin configuration revision, complete inventory and provider resource hashes, expire after five minutes, and are consumed exactly once. Apply re-reads inventory/resources and refuses changes. Before a private domain is enabled, all recorded resources and ACL attachment are re-read and the target's identity/fingerprint is refreshed. ACL matching uses `remote_ip`, with inversion disabled and an explicit non-empty CIDR list. This avoids trusting arbitrary forwarded client-IP headers. Configured IPv6/VPN CIDRs are included; there is no public fallback. Explicit public plans omit the domain ACL.

Cleanup requires absence of the VMID throughout all observed clusters, even if a stopped guest or a different generation holds that VMID. Inventory and resource identity/reference checks repeat before each deletion. Unrelated resources are retained. Provider APIs do not offer a cross-system transaction or a compare-and-swap conditional delete; immediate re-reads narrow but cannot eliminate a concurrent external-administrator race. Avoid concurrent manual edits during apply. No background reconciliation task deletes anything.

Intent is fsynced before each write; acknowledged UUIDs and fingerprints are fsynced afterward. An acknowledgment/readback gap remains `manualRecovery:true`; any known but unverified UUID is retained in the operation with an empty fingerprint and is not adopted as verified ownership. Provider failure does not imply absence. Config write success does not imply successful reconfigure. Partial/interrupted operations block mutations on that OPNsense and remain visible after restart. Credential/CA repairs are allowed while preserving workflow policy. Automated recovery only repeats service application when every mutation was durably recorded and current identity/fingerprints agree. Earlier partial workflows and ambiguous creates/deletes require manual provider inspection; automated rollback, automatic adoption and an admin resolution wizard are intentionally absent. Preserve the state file and ownership records during operator recovery.

## Updates, authentication and storage

Updates require explicit API requests and a running non-template container, creation identity, and fresh fingerprint. Per-container locks cover queued/running jobs and unacknowledged uncertain terminal states. The queue is limited to 32 active jobs, concurrency to two, history to 200, logs to 100 phase entries, and each execution to 30 minutes. There is no start/stop/reboot operation. Debian/Ubuntu use `apt-get update` then `apt-get -y upgrade` with noninteractive frontend; Alpine uses `apk update` then `apk upgrade`. Unsupported actual OS IDs fail before mutation. The reboot-required file is reported; absence is not a proof that reboot is unnecessary, particularly on Alpine.

The command runner invokes the installed OpenSSH client with a fixed `pct exec` command, validated host/user/port/VMID, explicit key/known-hosts files, `StrictHostKeyChecking=yes`, batch mode, and no caller-provided shell program. Key paths are operator-supplied server runtime configuration. Remote stderr/update output is discarded; inspection output is bounded and parsed as data. API logs intentionally expose execution phases, not raw remote output that could contain secrets. Existing update scripts may need an interactive terminal, download upstream code themselves, or exit without completing application-specific work; these behaviors require real-container acceptance. Timeout or lost SSH connection does not prove the remote command stopped, so the state remains uncertain until operator acknowledgement.

Auth uses [coreos/go-oidc](https://github.com/coreos/go-oidc) v3.21.0, [golang.org/x/oauth2](https://pkg.go.dev/golang.org/x/oauth2) v0.37.0, and [SCS](https://github.com/alexedwards/scs) v2.9.0; JWT cryptography uses go-jose v4.1.6 transitively. No bespoke passwords, signed cookies, sessions, JWT validator, or password database was built. OIDC token issuer/audience/signature/expiration, nonce, one-use state, S256 PKCE, and explicit subject/verified-email authorization are checked. State/nonce/verifier live in a server-side SCS session and expire after ten minutes. Successful login rotates session ID; session lifetime is eight hours with a thirty-minute idle limit and cannot exceed ID-token expiry. The browser receives only an opaque Secure/HttpOnly/SameSite=Lax session cookie. Access/refresh tokens and client secrets are not stored in sessions. Restart invalidates all sessions. OIDC discovery and HTTPS configuration fail closed, including non-HTTPS signing-key URLs and HTTPS downgrade redirects. The configured bearer token remains usable for setup/API access; it is loaded from env or a private secret file. Live mode with no adapters configured exposes only auth status and liveness, while protected APIs return 401.

Durable config, secrets, ownership, plans, operations, jobs, and demo resources share one atomic JSON state file. Directories use 0700; state/lock files use 0600. A process lock rejects a second server on the same directory. Writes use a same-directory temp file, file fsync, rename and directory fsync; persistence uncertainty blocks later mutations until restart/inspection. Secrets are plaintext at rest within that protected file: protect backups and the host. There is no external database. Demo and live state are mode-bound; reusing one mode's state in the other refuses startup. Demo CLI startup ignores live auth environment and secret files. A live failure never falls back to demo. Authentication session state is intentionally ephemeral and separate.

## Independent review repairs

Standards and Spec reviews found and reproduced stale-target recovery, CIDR ordering, missing-owned-resource repair, mutable disk-size identity, and verbose-output reboot detection defects. Regression coverage now exercises these paths. Recovery binds the original container fingerprint and repeats profile/conflict/route checks before each reconfigure. Fresh plans can explicitly recreate absent owned resources, preserve surviving UUIDs, and refuse foreign replacements or dependencies. Cleanup may skip proven-absent resources. Provider CIDR sets use one canonical form. Stable root-volume identity excludes resize options while freshness retains the full digest. Reboot detection retains only a short streaming marker suffix, not package output. These source/fixture repairs do not establish authentic provider acceptance.


## Existing policy reuse and automatic network resolution

Saved-config discovery uses only `GET caddy/reverse_proxy/search_access_list?current=1&rowCount=-1` plus `get_access_list/{uuid}` (wrapper `accesslist`), or only `GET kea/dhcpv4/search_subnet?current=1&rowCount=-1` plus `get_subnet/{uuid}` (wrapper `subnet4`). Both verify complete counts, UUID uniqueness, getters and normalized option dictionaries. Discovery errors are not empty inventories. `privateAccessListId` is an explicit optional UUID; unsuitable or dashboard-owned lists are visible but unavailable. There is no first-list choice or public fallback. Shared definitions never enter the ownership/cleanup ledger. Manual generated ACLs remain an explicit alternative and detached old owned ACLs are retained until reviewed owned cleanup.

The pinned KEA controller/model above defines these subnet endpoints and `subnet4.subnet`, `subnet_id`, description and option fields. Selection counts every subnet containing the target's intended IPv4. It does not take the first or longest prefix, use a configured UUID hint, or require equality with the host's address-derivation /24. Complete normalized definitions, target freshness and unique containment are bound to plans/operations and rechecked before ensure writes and each initial/recovery service application. No subnet mutation is supported by either provider adapter. Original reservation subnet UUIDs stay in ownership; cleanup reads all reservations and acts on verified recorded identities across topology changes. Legacy hints remain readable but do not control new resolution.

The pinned Caddy model declares `CustomCertificate` with `BlankDesc` Auto HTTPS. Normal creation omits it when no explicit advanced override is configured; there is no certificate UUID or `domainReady` prerequisite. The adapter never changes global TLS/DNS. Existing explicit custom certificates and verified app routes remain intact. Scheme/port are app-specific; new apps use explicit HTTP/80 values, not legacy firewall defaults. An older ledger without a route can migrate only from its fingerprint-verified handler (or an explicit app-route repair review).

Shared ACL fingerprints bind the whole normalized getter record. Only non-inverted `remote_ip` policies with explicit restricted canonical CIDRs are accepted. Missing/changed definitions block private preparation/enablement/recovery; public routes and cleanup do not depend on shared-policy suitability. Inspection shows the server's current shared policy separately from manually entered generated-mode CIDRs. As with all provider writes, cross-system atomicity is unavailable; immediate rechecks cannot eliminate a concurrent administrator edit between GET and mutation/reconfigure. Avoid concurrent manual topology/policy edits during application.
